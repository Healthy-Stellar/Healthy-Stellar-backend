# EHR Import Temp File Cleanup Bugfix Design

## Overview

The EHR import system writes unencrypted patient records to temporary files during processing. Currently, these temp files are only deleted on the success path. When any error occurs during reading, parsing, or downstream operations (IPFS, Stellar, database), the temp file remains on disk indefinitely with full unencrypted patient data. This creates a data security and compliance risk, particularly with malformed uploads which are a common failure case. The fix ensures temp files are always deleted regardless of where a failure occurs, implements encryption for temp files at rest, and establishes a scheduled cleanup mechanism for any orphaned files.

## Glossary

- **Bug_Condition (C)**: When any error occurs during EHR import processing (read errors, parse errors, IPFS/Stellar/database failures), the temp file is not deleted and remains on disk with unencrypted patient records
- **Property (P)**: The desired behavior when any error occurs - temp files must be deleted before the job terminates, ensuring no unencrypted patient data persists on disk
- **Preservation**: Successful imports must continue to delete temp files as before; file isolation between concurrent jobs must be maintained; only identified temp files are deleted, not entire temp directories
- **EhrImportProcessor.process()**: The job processor in `src/ehr-import/ehr-import.processor.ts` that orchestrates reading, parsing, anchoring, and storage of EHR records
- **TempStorageService**: The service in `src/ehr-import/services/temp-storage.service.ts` responsible for writing, reading, and deleting temporary files
- **tempFilePath**: The filesystem path to the temporary file containing the unencrypted patient records, generated by TempStorageService.writeBuffer()

## Bug Details

### Bug Condition

The bug manifests when any error occurs during the EHR import processing pipeline. The `EhrImportProcessor.process()` function catches errors at the read stage and parse stage but does not delete the temp file. Similarly, errors during IPFS upload, Stellar anchoring, or database storage propagate up without deleting the associated temp file. The temp file persists on disk with full unencrypted patient records, creating a data exfiltration and compliance risk.

**Formal Specification:**
```
FUNCTION isBugCondition(context)
  INPUT: context containing jobId, tempFilePath, and error from any stage
  OUTPUT: boolean
  
  RETURN (context.errorOccurred == true)
         AND (context.errorStage IN ['read', 'parse', 'ipfs', 'stellar', 'database'])
         AND (fileExists(context.tempFilePath) == true)
         AND (NOT isDeleted(context.tempFilePath))
END FUNCTION
```

### Examples

**Example 1: Read Error - Temp file left on disk**
- Input: Job attempts to read a temp file that is corrupted or inaccessible
- Current behavior: Line 54-60 catches the error, updates job status to FAILED, but does not delete tempFilePath
- Temp file remains on disk with patient data
- Expected: Temp file should be deleted before throwing

**Example 2: Parse Error - Temp file left on disk**
- Input: Job attempts to parse a malformed HL7/CCD/CSV file
- Current behavior: Line 63-70 catches the error, updates job status to FAILED, but does not delete tempFilePath
- Temp file remains on disk with patient data
- Expected: Temp file should be deleted before throwing

**Example 3: IPFS Upload Error - Temp file left on disk**
- Input: IPFS service fails during record upload (network timeout, service unavailable)
- Current behavior: Line 102-108 catches the error, logs it, but does not delete tempFilePath
- Job continues processing, eventually completes with errors, but tempFilePath is never deleted
- Expected: Temp file should be deleted when job finally completes or errors out

**Example 4: Stellar Anchoring Error - Temp file left on disk**
- Input: Stellar service fails during CID anchoring
- Current behavior: Line 119-128 catches the error but does not delete tempFilePath
- Job continues, eventually completes, but tempFilePath is never deleted
- Expected: Temp file should be deleted regardless of when Stellar fails

**Example 5: Edge case - Concurrent jobs with different temp files**
- Input: Multiple jobs processing different uploads simultaneously
- Current behavior: Each job has its own tempFilePath; deletion is per-file
- Expected: Only the specific temp file for each job is deleted, not other files

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Successful imports must continue to delete temp files at the end (existing line 182 behavior)
- Concurrent jobs must maintain file isolation - each job only deletes its own temp file
- Parser behavior must remain unchanged - only temp file deletion is added
- Record processing pipeline must remain unchanged - IPFS, Stellar, database operations unchanged
- Error logging must continue as before - all errors still recorded in ImportError table

**Scope:**
All success paths and all error paths that do NOT involve temp file deletion should be completely unaffected by this fix. This includes:
- Successful record processing and database storage
- Error logging in the ImportError table
- Job status transitions (PROCESSING → COMPLETED or FAILED)
- Deduplication checks and quarantine mode
- Concurrent job handling

## Hypothesized Root Cause

Based on the bug description and code analysis, the root causes are:

1. **Missing Finally Block**: The `process()` method lacks a finally block or centralized error handler to guarantee cleanup regardless of where errors occur. Currently deletion only happens in the success path at line 182.

2. **Multiple Error Paths**: The processor has multiple catch blocks (read error, parse error, per-record errors, batch errors) but none of them delete the temp file before exiting or propagating errors.

3. **No Encryption at Rest**: Even if files were cleaned up, they are stored unencrypted in the local temp directory, creating a window of vulnerability between write and delete.

4. **No Orphan Cleanup**: If a process crashes or is forcibly killed after writing temp files, orphaned files accumulate indefinitely on disk.

## Correctness Properties

Property 1: Bug Condition - Temp File Cleanup on All Error Paths

_For any_ error that occurs during EHR import processing (read, parse, IPFS, Stellar, database), the fixed EhrImportProcessor.process() function SHALL delete the associated temp file before the job completes or throws, ensuring no unencrypted patient data persists on disk.

**Validates: Requirements 1.1, 1.2, 1.3, 2.1, 2.2, 2.3**

Property 2: Preservation - Success Path and File Isolation

_For any_ successful import or concurrent job scenario where no error occurs (or errors are handled internally), the fixed code SHALL produce exactly the same behavior as the original code, including temp file deletion in the success path and maintaining file isolation between concurrent jobs.

**Validates: Requirements 3.1, 3.2, 3.3**

## Fix Implementation

### Changes Required

Assuming the root cause analysis is correct, the fix involves three coordinated changes:

**File 1: `src/ehr-import/ehr-import.processor.ts`**

**Function**: `process()`

**Specific Changes**:

1. **Add Finally Block for Guaranteed Cleanup**:
   - Wrap the entire job processing logic in try-catch-finally
   - In the finally block, unconditionally delete the temp file if it exists
   - This ensures cleanup happens regardless of success or failure
   - Implementation: Add finally block at end of process() method that calls `await this.tempStorage.deleteFile(tempFilePath)` with error suppression

2. **Remove Redundant Deletion from Success Path**:
   - Line 182 currently deletes the file on success
   - After adding finally block, remove this line to avoid double-deletion attempts
   - Finally block handles all cleanup

3. **Ensure Error Propagation Does Not Skip Cleanup**:
   - Current catch blocks update job status and re-throw errors
   - With finally block, temp file will be deleted even when errors propagate
   - No additional changes needed in individual catch blocks

**File 2: `src/ehr-import/services/temp-storage.service.ts`**

**Function**: `writeBuffer()` and new encryption support

**Specific Changes**:

1. **Add Encryption for Temp Files at Rest**:
   - Generate a random encryption key per temp file or use a master key from config
   - Encrypt buffer before writing to disk
   - Store encryption metadata (IV, algorithm) alongside file or in filename
   - Implementation: Before fs.writeFileSync(), encrypt buffer; after readFileSync(), decrypt buffer

2. **Add Encryption to readFile()**:
   - Detect if file is encrypted and decrypt on read
   - Implementation: After fs.readFileSync(), decrypt buffer before returning

3. **Graceful Degradation for Missing Keys**:
   - If encryption is not configured, write unencrypted (backward compatible)
   - Implementation: Check if encryption key is available; skip encryption if not

**File 3: New file `src/ehr-import/services/temp-file-sweeper.service.ts`**

**Function**: Scheduled cleanup of orphaned temp files

**Specific Changes**:

1. **Create TempFileSweeperService**:
   - Scan temp directory for files older than a threshold (e.g., 24 hours)
   - Delete files that match the temp file naming pattern and are stale
   - Log sweep results
   - Implementation: Use node cron or NestJS scheduler to run periodically

2. **Add Sweep Schedule Configuration**:
   - Make sweep interval configurable via environment variable
   - Default to once per day or every 6 hours
   - Implementation: Add EHR_IMPORT_TEMP_SWEEP_INTERVAL config parameter

3. **Integrate into EHR Import Module**:
   - Register TempFileSweeperService in EhrImportModule
   - Start sweeper on module initialization
   - Implementation: Add service to module providers and call onModuleInit()

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code by simulating various error conditions, then verify the fix works correctly (temp files deleted) and preserves existing behavior (success path unchanged, file isolation maintained).

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm that temp files are NOT deleted when errors occur on unfixed code. This validates our root cause analysis.

**Test Plan**: Create integration tests that simulate error conditions at each stage (read, parse, IPFS, Stellar, database) and verify that temp files remain on disk after the job fails. Run these tests on UNFIXED code to observe failures and understand the root cause.

**Test Cases**:

1. **Read Error Test**: Create a corrupted temp file path, attempt to process it, verify read error occurs and temp file is NOT deleted (will fail on unfixed code, pass on fixed)

2. **Parse Error Test**: Write a malformed HL7/CCD/CSV buffer, attempt to process it, verify parse error occurs and temp file is NOT deleted (will fail on unfixed code, pass on fixed)

3. **IPFS Error Test**: Mock IPFS service to throw error, attempt to process valid record, verify error occurs and temp file is NOT deleted (will fail on unfixed code, pass on fixed)

4. **Stellar Error Test**: Mock Stellar service to throw error, attempt to process valid record, verify error occurs and temp file is NOT deleted (will fail on unfixed code, pass on fixed)

5. **Database Error Test**: Mock database to throw error, attempt to process valid record, verify error occurs and temp file is NOT deleted (will fail on unfixed code, pass on fixed)

**Expected Counterexamples on Unfixed Code**:
- Temp files remain on disk after read errors
- Temp files remain on disk after parse errors
- Temp files remain on disk after IPFS/Stellar/database errors
- File count in temp directory increases without corresponding deletions

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds (errors occur), the fixed function deletes the temp file.

**Pseudocode:**
```
FOR ALL errorCondition IN [read_error, parse_error, ipfs_error, stellar_error, database_error] DO
  tempFilePath := createTempFile()
  TRY
    process(jobId, tempFilePath, errorCondition)
  CATCH error
    -- Expected to catch error
  END TRY
  ASSERT fileExists(tempFilePath) == false
END FOR
```

### Preservation Checking

**Goal**: Verify that for inputs where the bug condition does NOT hold (success path), the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL successScenario IN [valid_hl7, valid_ccd, valid_csv] DO
  tempFilePath := createTempFile(successScenario)
  ASSERT fileExists(tempFilePath) == true BEFORE processing
  result := process(jobId, tempFilePath, successScenario)
  ASSERT result.status == COMPLETED
  ASSERT fileExists(tempFilePath) == false AFTER processing
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many valid record combinations automatically
- It catches edge cases in success scenarios that manual tests might miss
- It provides strong guarantees that success behavior is unchanged
- It verifies file isolation across concurrent jobs

**Test Plan**: Observe success behavior on UNFIXED code (temp files are deleted), then write property-based tests capturing that behavior and verify it continues after fix.

**Test Cases**:

1. **Success Path Preservation**: Generate valid EHR records across formats, verify job completes successfully and temp file is deleted (same as unfixed behavior)

2. **Concurrent Job Isolation**: Spawn multiple concurrent jobs with different temp files, verify each job deletes only its own temp file (same as unfixed behavior)

3. **Partial Failure Isolation**: Process batch with some records failing, verify temp file is still deleted at end (unfixed behavior: file was deleted even with failures within batch, fixed should preserve this)

4. **Encryption Transparency**: Verify encrypted temp files are readable after write and decrypted correctly (new behavior, no regression)

### Unit Tests

- Test TempStorageService.deleteFile() with missing files (should not throw)
- Test TempStorageService encryption/decryption of buffer round-trip
- Test TempFileSweeperService identifies stale files correctly
- Test TempFileSweeperService respects sweep threshold
